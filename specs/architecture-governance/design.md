# 背景与目标

日期：2026-10-09。状态：开发守则与设计基线；实现未开始。

用户要求先制定项目指南，以合理设计模式和 DDD 统一优化架构，然后再解决模型接入问题。本轮产物为根目录 `AGENTS.md`、详细开发指南和本决策记录，不修改业务代码或数据。

已核实：`backend/internal` 已分层；`application/catalog_service.go` 等文件包含 Gin handler；`domain/processor/processor.go` 直接依赖 WebSocket 和 I/O；`infrastructure/provider/bailian/client.go` 按名称前缀选择文本/图片协议；`domain/provider/speech.go`、`video_capability.go` 按固定 ID 提供能力。已有 Registry 以 vendor 路由，尚未实现独立协议绑定。

# 约束与边界

- **Constraints**：保留 Go + Gin、Vue 3、SQLite、本地任务及 EXE 交付；保护草稿、素材、历史任务、密钥与现有并发保护；本轮只写文档。
- **Assumptions**：同协议模型可以通过配置表达差异，但不同输入模式与异步协议仍需要已实现的适配能力；目标以模块化单体足够，尚无拆服务证据。
- **OpenQuestions**：首批新增协议清单、外部厂商的真实参数与响应契约、旧任务缺失快照的兼容范围。上述问题在后续规格阶段确认，不妨碍本轮守则编写。
- 非功能目标：业务规则可独立测试；同协议模型增补不改执行分支；配置变化可追溯；失败可解释；任务受理与恢复不重复计费；升级不丢数据。
- **SubSkills**：本轮使用 `speckit-design`；后续按任务使用 `speckit-specify`、`speckit-plan`、`speckit-tasks`、`speckit-implement`、`speckit-code-review`。框架适配沿用 Gin + Go、Vue + TypeScript 的仓库实践；当前未提供专门框架技能，不虚构已加载 `kratos-patterns`，也不迁移到 Kratos。

# 方案候选

## 观点审议

| 视角 | 主张 | 反对点 | 需要的证据 |
| --- | --- | --- | --- |
| 产品 | 已配置的能力在对应页面有一致表现，不可用时给出原因 | 用户勾选能力即宣称远端可用会制造新的误导 | 陌生 ID 的完整操作回归、失败提示、真实契约 |
| 架构 | DDD + 端口与适配器，分离配置、协议和执行 | 按模型建适配器或立即拆微服务都会扩大耦合与成本 | 依赖图、领域不变量、事务及任务恢复边界 |
| 开发 | 按纵向用例渐进迁移，保留现有持久化和测试 | 一次搬包或通用脚本引擎难以验证兼容性 | 旧配置/任务样本、协议夹具、回归和构建证据 |

## A：继续扩展模型白名单

- **Architecture**：沿用名称分支与厂商客户端，每个新型号增补判断。
- **Data**：不增加协议绑定；能力仍由代码提供，基本无需迁移。
- **API**：保留现状，仅改善错误信息。
- **Flow**：管理页声明能力 → 硬编码名单校验 → 厂商执行。
- **Risks**：UI 与执行规则继续分裂，同协议型号也依赖发版；补充断言只能降低回归风险，不能解决扩展问题。
- **Cost**：短期低，持续维护成本随型号增长。
- **Fit**：不满足用户的可扩展性目标及 `speckit-design` 的长期演进要求。

## B：模块化单体 + DDD + 协议适配与能力配置（选择）

- **Architecture**：创作、模型配置、生成执行、素材与成片逻辑分域；接口向内依赖；注册表按协议与操作选择适配器。
- **Data**：模型定义增加显式能力规格、协议绑定及修订；任务保存配置快照；凭据仍在密钥设施。先增加兼容字段，迁移已有配置，不在此阶段决定物理拆表。
- **API**：后续增加统一能力解析与可用原因，区分启用和验证状态；保持旧接口兼容，契约方案在规格阶段确定。
- **Flow**：配置能力 → 后端解析可执行规格 → 用例验证并冻结任务 → 适配器执行 → 状态管理与结果应用。
- **Risks**：迁移期间新旧规则可能并存；通过统一解析入口、显式兼容版本、协议契约与旧数据测试控制。
- **Cost**：中等，按操作纵向迁移；同协议模型增补长期成本低。
- **Fit**：满足用户 DDD、可读性及扩展性要求；遵循 `speckit-design` 的取舍、证据和迁移要求，使用当前 Gin 技术栈。

## C：可编程通用协议引擎或立即微服务化

- **Architecture**：任意请求模板/脚本、动态插件或远程服务化协议执行。
- **Data**：引入脚本/模板版本、部署及执行记录；服务化还需分布式状态和存储协调。
- **API**：新增插件管理或远程执行契约。
- **Flow**：配置模板/部署插件 → 动态解释执行 → 跨运行时映射结果与状态。
- **Risks**：调试、安全、类型约束和恢复复杂；沙箱与专门运维可缓解但代价高。
- **Cost**：高，无证据表明当前规模需要。
- **Fit**：超过用户当前需求，削弱可读性，不符合最小必要抽象原则。

# 权衡与决策

- **Decision**：选择 B。以领域规则定义边界，以适配器隔离技术差异，以配置表达同协议模型差异；先修正职责与契约，再迁移实现。
- **Rejected**：A 无法消除模型白名单根因；C 成本与当前产品规模不匹配。
- 选择的模式及使用条件写入 [开发指南](../../docs/development-guide.md)。不要求每个模式立即落地。
- 继承 [ADR 0001](../../docs/adr/0001-mvp-architecture.md) 的技术基线与异步任务方向，补充其尚未在代码中完全落实的依赖约束。新代码遵循新守则，旧债务按计划收敛。

# 风险与回滚

- 文档先行可能被误认为系统已支持任意模型：各文件明确标注目标状态；产品说明必须依据实际实现。
- 后续迁移可能影响运行中任务：保留协议版本和快照兼容路径，在规格中明确配置删除、密钥轮换和任务重试的行为。
- 数据结构变更应优先可加字段和幂等迁移；降级前确认旧版本是否能读取新数据，不兼容时使用配套数据库、素材和密钥备份恢复。
- 不把回退到旧白名单作为长期方案。兼容分支需列出用途、覆盖测试和退出条件。
- 本轮仅文档，可独立修订守则，不产生数据库或业务回滚需求。
